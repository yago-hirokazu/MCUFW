# Linux カーネル コーディング規約 要約

この文書は、Linux 2.6.24 の `Documentation/CodingStyle` を翻訳したもので、2008年時点の規約です。中心となる思想は、**技巧より可読性、深いネストより単純な構造、局所的な短さより保守のしやすさを優先する**ことです。[原文の日本語訳](http://archive.linux.or.jp/JF/JFdocs/kernel-docs-2.6/CodingStyle.html)

## 主要ルール

### 1. インデント

- インデントにはタブを使用し、表示幅は8文字とする。
- インデントに空白を使わない。
- 深すぎるインデントは、処理を関数に分割すべき兆候と考える。
- `switch` の `case` は `switch` と同じ深さに置く。
- 1行に複数の文や複数の代入を書かない。
- 行末に空白を残さない。

```c
switch (suffix) {
case 'G':
case 'g':
	mem <<= 30;
	break;
default:
	break;
}
```

### 2. 行の長さ

- 原則として1行80カラム以内。
- 長い式は、意味のまとまりごとに分割する。
- 継続行は元の行より明確に深くインデントする。
- ユーザーに表示する文字列は、検索しやすさを損なうため、不自然に分割しない場合もある。

### 3. 波括弧と空白

制御文はK&R形式です。開始波括弧を同じ行に置きます。

```c
if (condition) {
	do_something();
} else {
	do_something_else();
}
```

ただし、関数定義の開始波括弧は次の行です。

```c
static int process_item(int item)
{
	return item;
}
```

そのほかの原則：

- `if`, `for`, `while`, `switch` の後には空白を置く。
- 関数名と `(` の間には空白を置かない。
- 演算子の前後には適切な空白を置く。
- 本体が単文なら波括弧を省略してよい。
- ただし、`if` と `else` の片方だけが複文なら、両方に波括弧を付ける。
- 不要な空白を入れて見た目をそろえようとしない。

### 4. 名前の付け方

- C89の制約に合わせるだけの極端に短い名前は避ける。
- 名前は、その変数や関数の役割が分かるものにする。
- グローバルな名前は説明的にする。
- 短いローカル変数には、`i` や `tmp` のような短い名前を使ってよい。
- 型や用途を名前に埋め込むハンガリアン記法は使わない。
- `ThisVariableIsATemporaryCounter` のような長すぎる名前も避ける。

つまり、**スコープが広いほど説明的に、狭いほど簡潔に**します。

### 5. `typedef`

構造体やポインタを安易に `typedef` しないことを推奨しています。

```c
struct device *dev;
```

この形なら、変数が構造体へのポインタであることが明確です。`typedef` が許容されるのは、おおむね次の場合です。

- 完全に抽象化されたオブジェクト
- `u8`, `u32` のような明確な整数型
- 型安全性を高める専用型
- アーキテクチャ依存型
- 標準Cの既存型と同じ形式を踏襲する場合

### 6. 関数

- 関数は短くし、一つの仕事に集中させる。
- おおよその目安は、画面1～2枚程度。
- ローカル変数は5～10個程度までを意識する。
- 複雑な関数は小さな関数へ分割する。
- 関数間には空行を1行入れる。
- エクスポートする関数には、定義の直後に `EXPORT_SYMBOL()` を置く。
- 関数プロトタイプでは、引数名も記載する。

固定の行数制限よりも、**関数全体を理解しやすいかどうか**が重要です。

### 7. 終了処理の一元化

関数途中で資源を確保した場合は、`goto` を使って後始末を一元化してよいとされています。

```c
result = allocate_resource();
if (!result)
	return -ENOMEM;

buffer = allocate_buffer();
if (!buffer) {
	result = -ENOMEM;
	goto free_resource;
}

/* 通常処理 */

free_buffer:
	release_buffer(buffer);
free_resource:
	release_resource();
	return result;
```

`goto` は無条件に悪いものではなく、次の利点があります。

- ネストを浅くできる。
- 後始末処理の重複を防げる。
- 終了経路を一か所で管理できる。
- 資源解放漏れを減らせる。

ラベルには `err1` や `err2` より、`free_buffer` のように「何をするか」が分かる名前を付けます。

### 8. コメント

- コメントには「何をしているか」より、可能なら「なぜそうするか」を書く。
- 悪いコードをコメントで補うのではなく、コード自体を単純化する。
- 関数内部へ大量のコメントを入れることは避ける。
- 関数の先頭で、その目的と理由を説明する。
- 公開APIには `kernel-doc` 形式を使用する。
- この版では `//` を使わず、C89形式のコメントを使う。

```c
/*
 * 複数行コメントでは、各行の左側に
 * アスタリスクを並べる。
 */
```

### 9. 複雑なプリプロセッサ処理を避ける

- `#ifdef` が大量に入った読みにくいコードを避ける。
- 条件付き実装はヘッダーや専用関数へ隠す。
- マクロは、複数回評価や型の問題に注意する。
- 複数文マクロは `do { ... } while (0)` で囲む。
- マクロ内でフロー制御を隠さない。
- 関数にできる処理は、なるべく関数にする。

```c
#define DO_SOMETHING(x)		\
	do {			\
		prepare(x);	\
		execute(x);	\
	} while (0)
```

### 10. データ構造

- 参照カウントを持つデータ構造では、生成・参照・解放方法を明確にする。
- 並行処理されるデータでは、ロックや所有権の規則を明確にする。
- 構造体は「データの寄せ集め」ではなく、ライフサイクルを持つオブジェクトとして扱う。
- 誰が確保し、誰が所有し、誰が解放するかを設計段階で定める。

### 11. 戻り値

処理の成功・失敗を返す関数は、原則として次の慣習に従います。

- 成功：`0`
- 失敗：負のエラーコード

述語関数は次の形式です。

- 真：`1`
- 偽：`0`

計算結果やポインタを返す関数では、範囲外の値、`NULL`、`ERR_PTR()` などで失敗を示します。これらの規則を混同しないことが重要です。

## 全体を短くまとめると

Linuxカーネル流のコードは、次のようなコードです。

- タブ幅8のK&Rスタイル
- 行と関数を短く保つ
- ネストを浅くする
- 凝った式やマクロを避ける
- 名前から役割が分かるようにする
- コメントでは理由を説明する
- `goto` を含め、終了処理を単純化できる手段を合理的に使う
- 型、所有権、戻り値の意味を明確にする
- 「賢そうなコード」より「すぐ読めるコード」を選ぶ

なお、この資料は古い版なので、MCUFWの規約として適用する場合は、ここに記載された基本思想を軸にしつつ、現在のLinuxカーネル規約との差分を別途扱うのがよいでしょう。特に、現在は80桁制限やコメント、宣言位置など、一部の指針が更新されています。
